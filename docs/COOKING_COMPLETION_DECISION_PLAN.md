# 조리완료 판정 계획 (현장 운영 기준)

## 1. 목표
- 조리완료를 "모델 감"이 아니라 "설명 가능한 기준"으로 판정한다.
- 현장 운영에서 오판 리스크를 줄이고, 보고/감사 가능한 근거를 남긴다.

## 2. 판정 철학
- 시간은 필수 기준(최대 조리시간).
- 색/리프트는 보조 근거(품질 신호).
- 안전 측면에서 늦게 끄는 리스크를 우선 제어한다.

## 3. 왜 이 구조가 필요한가
- 현재 데이터는 양/품질이 불균일해 CNN 단독 운영은 리스크가 크다.
- 현장에서는 "일관성"과 "재현성"이 모델 성능 숫자보다 중요하다.
- 완료 판정 근거를 수치로 설명 가능해야 조직/기관 대응이 가능하다.

## 4. 운영 판정 구조 (v1)
- 준비 구간: `target_time - 60초` 이전에는 완료 판정 금지
- 후보 구간: `target_time - 20초` 이후 완료 후보 허용
- 근거 확인: 색 변화 또는 리프트 신호 중 하나 이상 충족 시 완료
- 상한 강제: `target_time + 15초` 도달 시 강제 완료
- 디바운스: 완료 후 재판정 금지

## 5. 입력 신호 정의
- 시간 근거: `running_time_sec`
- 색 근거: 최근 구간 `color_delta` 수준 및 추세
- 동작 근거: `lift_count`, 최근 lift 발생 시점
- 상태 근거: `process_type`, `mode`, `cleaning`, `human_block`

## 6. 예외/품질 정책
- 청소 모드, 무레시피, 비조리 상태는 판정 중지
- 메타/센서 누락 시 시간 단독 보수판정으로 fallback
- `target_time` 불일치 시 메타 최빈값(조리/배출 구간 우선)으로 정정

## 7. 결과 분류
- `AUTO_COMPLETE`: 시간 + 보조신호 충족
- `TIME_LIMIT_COMPLETE`: 상한 시간 초과로 강제 완료
- `PENDING_REVIEW`: 신호 충돌/누락으로 보류

## 8. 보고 포맷 (필수 저장)
- 완료 시각
- `target` 대비 실제 `running` 차이(초)
- color 근거(값/추세)
- lift 근거(횟수/최근 시점)
- 판정 타입(AUTO/TIME_LIMIT/PENDING)

## 9. 단계별 실행 계획
- 1단계(즉시): 규칙 기반 완료판정 고정, 로그/리포트 자동화
- 2단계(2~3주): 음식군별 임계값 분리(돈까스/교자/치킨 등)
- 3단계(데이터 확보 후): CNN 점수는 보조 지표로 병합
- 4단계: 조건부로만 CNN 주판정 허용

## 10. 기대효과
- 지금 데이터 상태에서도 즉시 운영 가능
- 판정 근거가 명확해 현장/보고 대응이 쉬움
- 이후 AI 고도화 시 기존 운영 안정성을 유지 가능
